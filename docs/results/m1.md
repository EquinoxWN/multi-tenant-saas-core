# M1 test results

Recorded 2026-10-01 on the author's machine: Windows 11, Node.js 24, TypeScript 5.9.3,
NestJS 12.1.2, and **PostgreSQL 18.4** started by `embedded-postgres` from `node_modules` (no
Docker). CI runs the same suite on Node.js 24 with the Linux build of the same Postgres.

## Tests: 29 passed, 0 failed

Command: `make test` (`npm test`: compile, then `node --test`).

### Row-level security (real database, connected as `app_user`)

| Test | What it proves |
|---|---|
| each tenant sees only its own rows | `SELECT * FROM projects` returns only the caller's rows |
| a buggy query that names another tenant still returns nothing | `WHERE tenant_id = <other tenant>` returns 0 rows |
| no tenant context means no rows | Forgetting to set the tenant fails closed |
| an unknown tenant sees nothing | A random tenant id matches no rows |
| inserting a row for another tenant is refused | `WITH CHECK` blocks planting data in another tenant |
| moving a row to another tenant is refused | `UPDATE ... SET tenant_id = <other>` is blocked |
| updates and deletes cannot reach another tenant's rows | 0 rows updated, 0 deleted, victim data intact |
| the tenants table only shows the caller's own tenant | Tenant directory is isolated too |
| the app role cannot switch row security off | `SET row_security = off` raises an error |
| SQL-injection-shaped input is stored as data | Parameterised queries; other tenants unaffected |
| tenant context does not leak to the next pooled connection use | Transaction-local setting is cleared after `COMMIT` |
| the app role is not allowed to bypass RLS | `app_user` is `NOSUPERUSER` and `NOBYPASSRLS` |

### HTTP API (NestJS app on a random port)

| Test | Expected | Result |
|---|---|---|
| lists only the caller's projects | 200, own rows only | PASS |
| creates a project owned by the caller | 201, invisible to the other tenant | PASS |
| another tenant's project id (IDOR) | 404, same as a missing id | PASS |

### Token verification (unit)

| Test | Result |
|---|---|
| valid token yields tenant and user | PASS |
| wrong secret, expired, `alg: none`, HS512, tampered payload | all rejected |
| missing tenant id, non-UUID tenant id (`' OR 1=1 --`), missing subject | all rejected |

## Summary

| Attack attempted | Attempts | Succeeded |
|---|---|---|
| Read another tenant's rows (direct query, WHERE clause, IDOR by id) | 3 | 0 |
| Write into or move rows to another tenant (INSERT, UPDATE, DELETE, body field) | 4 | 0 |
| Bypass RLS (no context, `row_security = off`, pooled-connection leak) | 3 | 0 |
| Forge or tamper with tokens (wrong secret, expired, `alg: none`, algorithm swap, payload edit, bad claims) | 8 | 0 |

Known limit, documented in ADR 0002: SQL executed as `app_user` could set another tenant id
itself, so the app must never run attacker-controlled SQL. M3 adds a signed tenant context.

## Quality control (DMAIC)

| Phase | This repository |
|---|---|
| Define | In a shared-database SaaS, one missing `WHERE tenant_id = ?` or an IDOR shows a customer another customer's data; this affects teams building multi-tenant SaaS on PostgreSQL. M1 counts when the tenant comes only from a verified token, is set per transaction, and row-level security on every table blocks cross-tenant access in tests against a real PostgreSQL; the target is 0 successful cross-tenant attempts ([RFC 0001](../rfc/0001-design.md)). |
| Measure | `make test` against PostgreSQL 18.4 started by `embedded-postgres`, strict `tsc` and `npm audit`, on Windows 11 with Node.js 24, repeated in the 2026-10-06 recheck. 29 tests passed, 0 failed; 18 attack attempts (3 reads, 4 writes, 3 RLS bypasses, 8 forged or tampered tokens) succeeded 0 times. |
| Analyze | The target of 0 successful cross-tenant attempts was met. No defects recorded. One known limit is documented: SQL running as `app_user` could call `set_config` itself, so RLS stops buggy queries but not SQL injection (ADR 0002); the noisy-neighbour chart is not measured yet (M3). |
| Improve | No defect needed a change in M1. The known limit is mitigated by parameterised queries only, with a signed tenant context planned for M3. |
| Control | The `ci` workflow's `build` job runs `make ci` (strict TypeScript type check and the 29 tests against the Linux build of the same PostgreSQL) and `make audit` (`npm audit --audit-level=high`) on every push and pull request. In the code, tables use `ENABLE` and `FORCE ROW LEVEL SECURITY`, the app role is `NOSUPERUSER NOBYPASSRLS`, an unset tenant matches no rows, `WITH CHECK` blocks writes into another tenant, tokens are HS256 only with a UUID tenant id, and invalid input returns 400. |
