# Quality check, 2026-11-01

The owner's 10 rules, checked against the code on Windows 11 with Node.js 24.19.0 and PostgreSQL
18.4 from `embedded-postgres` (no Docker).

| # | Rule | Status | Evidence |
|---|---|---|---|
| 1 | Assume every call can fail | fixed | The API pool had no timeouts, so a dead or stalled database hung requests indefinitely. `poolConfig` (`src/db/database.ts`) now sets `connectionTimeoutMillis` 5 s, `statement_timeout` 10 s, `query_timeout` 15 s and `idle_in_transaction_session_timeout` 15 s; the migration client gets a 10 s connect timeout. `withTenant` swallowed a failed `ROLLBACK` (`.catch(() => undefined)`) and returned the connection to the pool in an unknown state; it now passes the error to `client.release(err)`, which destroys the connection, and still rethrows the original error (`test/database.test.ts`). The guard's bare `catch` maps every token error to one 401 on purpose (no oracle for attackers). Test harness: on Windows the suite hung intermittently (3 times in about 35 runs during this check) because PostgreSQL 18 I/O worker children outlived the embedded server and kept its pipes open, so `stop()` never resolved, and the test pools had no timeouts. `test/support/postgres.ts` now starts the server with `io_method=sync` and gives the test pools connect and query timeouts; three consecutive full runs then passed with no PostgreSQL process left. |
| 2 | Writes safe to retry | fixed | `POST /projects` created a new row on every retry. It now accepts an optional `Idempotency-Key` header (1 to 200 visible ASCII characters); migration `002_project_idempotency_key.sql` adds a nullable column with a partial unique index on `(tenant_id, idempotency_key)`, and the insert uses `ON CONFLICT ... DO NOTHING` then reads the existing row through RLS. Tests: retry returns the same id and one row; the same key in another tenant is a separate project; no key keeps the old behaviour. Migrations are recorded in `schema_migrations` and each runs in a transaction. |
| 3 | No race conditions | fixed | Two migrators starting together could both read `schema_migrations` before either committed and apply the same file twice. `migrate` now holds a session advisory lock (`pg_advisory_lock`) for the whole run; `test/migrate.test.ts` runs two migrators at once on a slow migration and asserts it is applied exactly once. Concurrent `POST`s with one key are serialised by the unique index. Tenant context is transaction-local, so pooled connections cannot share it (existing test). |
| 4 | Don't trust the clock | pass | No durations are measured in code. Timestamps are `timestamptz DEFAULT now()` and returned with `toISOString()` (UTC). `GET /projects` orders by `created_at, id` for display only; no logic depends on that order. JWT expiry uses `jsonwebtoken` with a 5 s clock tolerance. |
| 5 | Read before changing | pass | `pg` options were checked in the installed `@types/pg` and `pg/lib/defaults.js`. Env vars `DATABASE_URL`, `JWT_SECRET`, `PORT`, `DATABASE_ADMIN_URL`, `TEST_DATABASE_URL` are all in the README; `PORT` (default 3000) was added. |
| 6 | Never break compatibility | pass | Migration 002 only adds a nullable column and a partial index; existing rows and clients without the header are unchanged. The API response shape is unchanged. Building the unique index takes a write lock on `projects` for its duration (small table here); on a large live table it would be built `CONCURRENTLY` outside a transaction. |
| 7 | One source of truth | pass | No caches. Node 24 agrees across `engines`, CI and README. |
| 8 | Small changes, no secrets, validate input | fixed | Secret grep: only throwaway values in tests (random per run). Inputs: token (HS256 only, UUID tenant, subject), project name (1 to 100 chars), project id (UUID or 404), the new header (400 on invalid), config (`loadConfig` refuses a missing URL, a secret under 32 characters and a bad port; it had no tests, now `test/config.test.ts`). No new dependency. |
| 9 | Tests that can actually fail | fixed | No skips or tautologies. Mutation check below. |
| 10 | Re-verify | pass | `npm run lint`: no errors; `npm test`: see `docs/results/m1.md`; `npm audit --audit-level=high`: found 0 vulnerabilities; `audit_repo.py multi-tenant-saas-core`: OK. |
